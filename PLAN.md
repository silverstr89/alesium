# План: выплата прибыли трейдеру

Версия: 2 · Статус: одобрен по допущению (вопросы ниже, ответы по умолчанию отмечены) · срез 1 сделан и исправлен после сессии

## Цель
Трейдер просит выплату — получает 80% прибыли сверх начального баланса ровно один раз, даже при повторах API, рестартах движка и таймаутах провайдера; счёт начинает заново с начального баланса.

## Выплата по шагам: кто, в каком порядке, что в журнале

До запроса баланс = начальный (I) + прибыль (P).

| Шаг | Кто | Что делает | Что в журнале после шага | Баланс после шага |
|---|---|---|---|---|
| 1 | API → движок | Команда `payout` с `cmdId`. Движок проверяет: счёт активен, открытых позиций нет, прибыль > 0. Считает долю трейдера (80%, до цента одним округлением, half away from zero) и долю фирмы (остаток, чтобы сумма сошлась до цента). Баланс → начальный; порог дня опускается на прибыль, но не ниже порога нового счёта. Создаёт запись выплаты `payout-<seq>` со статусом `requested` и `reference` = `<id счёта>:payout-<seq>`. | `payout` (cmdId) — запрос выплаты | I |
| 2 | Движок → API | Отвечает только после коммита батча с этой записью (исправление из Части 1). | без изменений | I |
| 3 | Отправитель выплат | Один проход на счёт за раз. Берёт снапшот (в нём только закоммиченное) и для каждой `requested`: спрашивает `status(reference)`; если провайдер её не знает и с запроса прошло меньше 23 часов — `send({ reference, traderId, amount })`. `reference` берётся из снапшота: он вычисляется при запросе из id счёта и id выплаты, один и тот же при любом повторе и уникален между счетами. `cmdId` не годится — его выбирает клиент; `traderId:payoutId` тоже — у двух счетов одного трейдера одинаковые `payout-<seq>`. | без изменений | I |
| 4а | Отправитель → движок | Провайдер заплатил (или `status` = `paid`) → системное событие `payout-result: paid`. | `payout-result paid` | I |
| 4б | Отправитель → движок | Провайдер отказал (или `status` = `failed`) → `payout-result: rejected`; деньги возвращаются на счёт. | `payout-result rejected` | I + P |
| 4в | Отправитель | Таймаут: деньги могли уйти, а могли нет — это не отказ. Ничего не пишем; следующий проход спросит `status()`. | без изменений (выплата остаётся `requested`) | I |

## Что может пойти не так и что защищает

| Шаг | Сбой | Защита |
|---|---|---|
| 1 | API не получил ответа и повторяет команду | Тот же `cmdId` с тем же содержимым возвращает тот же результат и тот же `payoutId`; вторая выплата не создаётся. |
| 1 | Тот же `cmdId` с другой командой | Отказ `cmd-id-reused` (Часть 1). |
| 1 | Открыты позиции / нет прибыли / счёт провален | Отказ `positions-open` / `no-profit` / `account-failed`; ничего не меняется. |
| 1 | Выплата срабатывает как дневной убыток | Выплата — не убыток: порог дня (`dayFloor`) опускается на прибыль, поэтому запас до лимита на сегодня не меняется; но не ниже порога нового счёта — прибыль, заработанная сегодня и выведенная, не даёт лишнего запаса. Отказ провайдера возвращает порог. База дня не трогается. (В версии 1 сдвигалась база, а порог — только на 95% прибыли: счёт в минусе за день проваливался на собственной выплате.) |
| 1 | Округление | Доля трейдера округляется до цента один раз, из точного значения; фирма получает остаток — сумма долей равна прибыли до микро. |
| 2 | Коммит упал | Движок останавливается, команда получает ошибку, ничего не отправлено (Часть 1). |
| 2→3 | Отправка до записи в журнал | Отправитель видит только снапшот, а снапшот ждёт коммита своего `seq`. |
| 3 | Рестарт до отправки | После восстановления выплата `requested`; отправитель отправляет её. |
| 3→4 | Рестарт после отправки, до записи результата | `status()` = `paid` → пишем `paid`, повторно не отправляем. |
| 3 | Два отправителя одновременно | Проходы для одного счёта идут по очереди, даже на движке, перезапущенном в том же процессе. (В версии 1 считалось, что хватает одинакового `reference`, — нет: один проход получал отказ и возвращал деньги на счёт, другой в это время платил.) Между процессами — аренда на счёт (срез 2). |
| 3 | Два счёта одного трейдера | `reference` содержит id счёта и вычисляется при запросе; отправитель его не собирает. |
| 4в | Таймаут | Не отказ: деньги не возвращаем; `status()` на следующем проходе решает. |
| 4 | Провайдер помнит `reference` только 24 часа | Сделано: если провайдер выплату не знает, а с запроса прошло 23 часа или больше, отправитель её не шлёт — она ждёт человека (тревога — срез 2). Отправка всегда позже запроса, поэтому любая прошлая отправка провайдеру ещё памятна. |
| — | Катящийся деплой и откат | Версия без выплат принимает запись `payout` за отказанное закрытие и оставляет выплаченную прибыль на балансе; отказ в неизвестном типе есть только начиная с этой версии. Поэтому: сначала выкатить отдельно проверку неизвестного типа, потом версию с выплатами (выключатель команды — срез 2), потом включить команду; после первой выплаты откат ниже этой версии запрещён. Снапшот версии до выплат дополняется при восстановлении; id счёта передаётся явно. Записи сделок, написанные версией без выплат, эта версия пересчитала бы с новым округлением — нужна версия правил в записи. |

## Срезы, от меньшего к большему

1. **Этот срез (в памяти, с тестами):** команда `payout`, отправитель с `FakePayoutProvider`, результат в журнале, повторы API и рестарты.
2. Отправитель как фоновый цикл с паузой после таймаута и арендой на счёт; метрики и тревоги: выплата висит дольше N минут, выплата задержана после 23 часов. Запись «отправка начата» в журнал перед первой отправкой — тогда задерживать придётся только выплаты, которые действительно отправлялись.
3. Настоящий провайдер по HTTP: таймауты, вебхуки о статусе (с проверкой подписи), Postgres-журнал и снапшоты.
4. Лимиты выплат, KYC, ручное подтверждение крупных выплат.

## Вопросы к вам

1. Отказ провайдера: возвращаем на счёт всю прибыль (раздел не состоялся) или только долю трейдера? → **по умолчанию всю прибыль**: выплаты не было, фирма свою долю тоже не берёт.
2. Можно ли выплачивать с проваленного счёта? → **по умолчанию нет** (`account-failed`).
3. `status()` помнит `reference` те же 24 часа, что и `send()`? → **по умолчанию да**, поэтому после ~23 часов — только ручной разбор.
4. 80% — для всех программ или своя доля у каждой? → **в этом срезе константа**; станет полем программы, когда появится вторая.
5. Откуда `traderId` и id счёта? → **id счёта задаётся при создании (по умолчанию UUID) и хранится в снапшоте; `traderId` в этом срезе — параметр отправителя**; в продакшене оба — из учётной записи.
6. Долю фирмы проводим на счёт фирмы внутри движка или просто списываем с баланса трейдера? → **в этом срезе списываем**, сумма хранится в записи выплаты (`firmShare`) для сверки.
7. Есть ли лимит на частоту или сумму выплат? → **в этом срезе нет**; лимиты — срез 4.
8. Порог дня после выплаты: запас до лимита сохраняется, но не больше, чем у нового счёта? → **по умолчанию да**. Отказ в день запроса возвращает порог на тот же сдвиг; отказ в другой день считается так, будто возврат был в базе дня.
9. Доля трейдера: до ближайшего цента или вниз в пользу фирмы? → **по умолчанию до ближайшего**, half away from zero, как любая проводка.
10. Часы: `requestedAt` ставит секвенсор, а 23 часа отсчитывает отправитель по своим часам. → **запас в час покрывает расхождение**; если часы могут расходиться больше — считать по времени провайдера.

- Тесты среза: деньги доходят до провайдера ровно один раз при повторе API и рестарте посередине (до отправки и после отправки до записи результата); отказ возвращает деньги на счёт; таймаут — не отказ (и «до оплаты», и «после оплаты»); выплата не срабатывает как дневной убыток; повтор `cmdId` даёт тот же результат.

## Ожидаемые результаты (посчитаны до кода)
Начальный баланс 100 000.00, прибыль 1 000.01:
- доля трейдера: 1 000.01 × 0.8 = 800.008 → **800.01** (half away from zero);
- доля фирмы: 1 000.01 − 800.01 = **200.00**;
- баланс после запроса: **100 000.00**; после отказа провайдера: **101 000.01**.

## Итог

**Работает (срез 1, в памяти):**
- Команда `payout` (`src/apply.ts`): 80% прибыли трейдеру (одно округление), остаток фирме, баланс → начальный, порог дня опускается на прибыль, но не ниже порога нового счёта; отказы `positions-open`, `no-profit`, `account-failed`; тот же `cmdId` — тот же результат.
- Событие `payout-result`: `paid` или `rejected` (вся прибыль и порог дня возвращаются); повторный или запоздавший результат ничего не меняет.
- Отправитель `settlePayouts()` (`src/payouts.ts`): один проход на движок за раз, работает по снапшоту (только закоммиченное), сначала `status()`, затем `send()` с `reference` из журнала; таймаут — не отказ; после 23 часов неизвестная выплата ждёт человека.
- Движок: исключение в `apply()` останавливает его; снапшот версии до выплат восстанавливается с явным id счёта.
- Тесты (`test/payout.test.ts`, 21): деньги уходят ровно один раз при повторе API и рестарте до отправки, при рестарте после отправки до записи результата, когда провайдер уже не игнорирует повторы, при двух проходах сразу и через 25 часов после таймаута; у двух счетов одного трейдера — каждая выплата; ничего не отправляется до записи запроса в журнал; отказ возвращает деньги и порог дня; таймаут «до оплаты» и «после оплаты» — не отказ; выплата не срабатывает как дневной убыток и не даёт запаса больше, чем у нового счёта; отказ на следующий день считается по правилам нового дня. Защиты от двойной выплаты и от неверного порога проверены поломкой.
- Весь набор: 66 тестов, typecheck чистый.

**Не проверено:** настоящий провайдер и Postgres — по условию среза только `FakePayoutProvider` и `MemoryJournal`.
