# Разбор `AI_REVIEW.md` (`feature/journal-engine` → `main`)

Вердикты о поведении кода проверены запуском на ветке пулл-реквеста. Пункты про Postgres и миграцию (№6, №12) проверены чтением кода: базы в задании нет. Инварианты — из README; ревью проверяется против них.

Вердикты: **реальный баг** / **не баг** / **нужно решение**. Для каждого исправленного бага есть тест, который падал до исправления (история коммитов: сначала красные тесты, потом исправления).

## 13 пунктов ревью

| № | Пункт | Вердикт | Почему | Статус |
|---|---|---|---|---|
| 1 | Команда получает ответ раньше, чем записана | **Реальный баг** | `submit()` отвечал, не дожидаясь `append`; при упавшем коммите — `ok`, журнал пуст, позиция только в памяти. README: ответ — только после коммита батча. | Исправлено |
| 2 | Упавший коммит теряется: добавить ретрай | **Реальный баг, исправление ревью неверное** | Ошибка проглатывалась (`#flush` удалял промис в обоих случаях), движок шёл дальше и писал seq 2 без seq 1. Ретрай же запрещён README и опасен: коммит, упавший по таймауту, мог пройти, и повтор упрётся в первичный ключ. Правильно — остановить движок и отказать всем неотвеченным. | Исправлено (остановка, без ретрая) |
| 3 | Повторный `cmdId` возвращает старый результат | **Реальный баг** | Содержимое не сравнивалось: `open buy 1` и `open sell 5` с одним `cmdId` оба получали `ok, p1`. README: тот же `cmdId` с другим содержимым — отказ. Цена в содержимое не входит: её ставит секвенсор, и у повтора она может быть другой. | Исправлено (`cmd-id-reused`) |

## «Проверено, всё в порядке» — все четыре утверждения неверны

| Утверждение ревью | Вердикт | Почему | Статус |
|---|---|---|---|
| `apply()` детерминирован, время только из `entry.at` | **Реальный баг** | `openedAt` брался из `new Date()`: один журнал давал разные счета, восстановленный счёт отличался от исходного. | Исправлено (`openedAt = entry.at`) |
| Повторное чтение записи снапшота безвредно | **Реальный баг** | `read(from.seq)` включал запись снапшота; у системных событий нет `cmdId`, корректировка применялась дважды: +250 → +500 после рестарта. | Исправлено (`read(from.seq + 1)`) |
| Батчи не могут перемешаться | **Реальный баг** | Новый flush стартовал, пока предыдущий `append` был в полёте: seq 2 коммитился раньше seq 1. | Исправлено (один батч за раз) |
| Смещение Никосии верное | **Реальный баг** | Жёстко UTC+2, летом там UTC+3: 2026-07-15T21:30Z — уже 16 июля. | Исправлено (часовой пояс Asia/Nicosia) |

## Что ревью пропустило

| Находка | Вердикт | Почему | Статус |
|---|---|---|---|
| `PgJournal.read` глотает ошибки и возвращает `[]` | **Реальный баг** | Упавшее чтение при рестарте давало снапшот без хвоста журнала; движок затем выдавал уже занятые номера. | Исправлено: ошибка пробрасывается |
| `restore` принимает дыры в `seq` | **Реальный баг** | `apply` брал `seq` из записи вслепую; журнал с дырой восстанавливался молча. | Исправлено: дыра — отказ стартовать |
| `EngineOptions` игнорируются | **Реальный баг (мелкий)** | `maxBatchSize: 2` писал один батч из 5; описанный `retry` не существовал и противоречил README. | Исправлено: опции работают, `retry` удалён |
| Цена закрытия не проверяется | **Нужно решение** | Закрытие по отрицательной цене принималось (открытие проверяло цену, закрытие — нет). | Исправлено по допущению: цена ≤ 0 → `bad-command` |
| `fee()` и `pnl()` округляют до микро, `post()` — ещё раз до центов | **Реальный баг** | README: сумма округляется до центов только при зачислении. Двойное округление сдвигает проводку на цент: комиссия 0.0049995 списывалась как 0.01 (надо 0.00); убыток 4 999.9949995 — как 5 000.00 (надо 4 999.99), и счёт проваливался ровно на дневном лимите. На 300 000 случайных сделок — 31 проводка с ошибкой в цент. Старый тест комиссий сверял код с ним самим (`fee()` в ожидании), поэтому ошибку не видел. | Исправлено после сессии |
| Неизвестный тип записи принимается за закрытие | **Реальный баг** | Запись, которую версия не знает (например, выплата из новой версии), молча становилась отказанным закрытием: старая версия при восстановлении оставила бы выплаченную прибыль на балансе. | Исправлено после сессии: отказ до любых изменений, движок останавливается. Защищает только версии начиная с этой: версия без выплат по-прежнему примет выплату за закрытие, поэтому после первой выплаты откат на неё запрещён |

## Три реальных бага, которые важнее всего, и их тесты

1. **№1 + №2 — ответ до коммита, ошибки коммита проглатываются.** Трейдер получает «ok» за сделку, которой нет в журнале и которая пропадёт после рестарта; в журнале появляются дыры.
   Тесты: `a command is answered only after its batch has committed`, `a failed commit fails the command and stops the engine`, `batches commit in seq order, one at a time`.
2. **Восстановление повторно применяет запись снапшота.** Каждый рестарт может повторить последнюю корректировку баланса: деньги появляются или исчезают.
   Тест: `a restart does not apply the snapshot's own entry again`.
3. **№3 — повторный `cmdId` с другим содержимым получает старый ответ.** Клиенту говорят, что команда выполнена, хотя она не выполнялась.
   Тест: `the same cmdId with different content is rejected`.

По заданию исправлен первый (отдельный коммит). Затем исправлены и остальные реальные баги — каждый со своим тестом:
`a retry of a command with a newly stamped price returns the first result`, `a cmdId named like an Object.prototype member is an ordinary id`, `posting rounds to whole cents half away from zero, exactly`, `openedAt comes from the entry, never from the clock`, `the trading day never moves backwards`, `a close at a price of zero or below is refused`, `in summer the trading day starts at 21:00 UTC (Nicosia is UTC+3)`, `the day boundary follows the switch to and from summer time`, `a restored account equals the account before the restart, field for field`, `restore refuses a journal with a gap`, `a snapshot resolves under steady traffic`, `maxBatchSize caps a batch`, `flushIntervalMs collects a batch before writing it`, `the journal keeps the payload column, so the old and the new version can run side by side`, `a failed read fails loudly instead of returning an empty journal`.

Защиты, исправленные по багам выше, проверены поломкой: при удалении краснеет свой тест. Несколько вспомогательных проверок движка и восстановления тестами не покрыты.

## Доработка после сессии (денежная корректность)

После сессии я проверил денежные операции ещё раз — независимыми проверками по округлению, дневному лимиту, идемпотентности и выплатам — и нашёл то, что пропустил. Для каждой находки сначала тест, который падал, потом исправление; каждое исправление ломал нарочно и видел красный тест.

| Что было | Чем грозило | Исправление | Тест |
|---|---|---|---|
| Двойное округление комиссии и P&L | Проводка на цент больше или меньше; счёт проваливается на дневном лимите из-за лишнего цента | P&L и комиссия считаются точно (1e-16 единицы) и округляются до центов один раз; доля трейдера при выплате — тоже | `a fee is rounded to cents once, from its exact value`, `a close posts P&L minus fee rounded once`, `a cent lost to double rounding cannot fail the account`, `every posting is the exact amount rounded to cents once (seeded trades)`; старый тест комиссий переписан на значения, посчитанные вручную |
| Выплата сдвигала базу дня, а порог — только на 95% прибыли | Счёт, потерявший сегодня 5 400 при лимите 5 500, проваливался на собственном запросе выплаты и оставался проваленным после отказа провайдера | Порог дня хранится на счёте; выплата опускает его на сумму прибыли, но не ниже порога нового счёта; отказ возвращает его обратно. База дня — как в README | `a payout on a losing day keeps the loss room left that day…`, `a refused payout puts the day back as it was…`, `after a payout the loss room is never more than a fresh account has` |
| `reference` = `traderId:payout-<seq>` | У двух счетов одного трейдера обе выплаты `payout-2`: провайдер считал вторую повтором, а мы записывали её как оплаченную — деньги не уходили | У счёта есть id; `reference` = `<id счёта>:<id выплаты>` вычисляется при запросе и хранится в снапшоте. В записи журнала его нет, поэтому при восстановлении снапшота версии до выплат id счёта нужно передавать всегда один и тот же | `two accounts of one trader: each payout reaches the provider under its own reference` |
| Два прохода отправителя одновременно | Один записывал отказ и возвращал деньги на счёт, другой в это время платил: и выплачено, и возвращено | Проходы для одного счёта идут по очереди, в том числе на движке, перезапущенном в том же процессе (между процессами — аренда на счёт) | `two sender runs at once and a refusal…`, `a sender run on a restarted engine waits for the run still going on the old one` |
| Отказ провайдера пришёл уже на следующий торговый день | Сдвиг порога за день запроса добавлялся к порогу нового дня: счёт проваливался раньше, чем позволяет README | Сдвиг применяется только в день запроса; в другой день возврат считается так, будто он был в базе дня | `a refusal after midnight counts the refund in the new day…` |
| Порог дня округлялся вверх | При базе с долями цента (начальный баланс с микро) счёт проваливался на микро выше порога README | Порог — точное `база × (1 − %)`, округлённое вниз до микро | `the daily floor is base × (1 − pct%) rounded down to a micro, never up` |
| Таймаут после оплаты, следующий проход через 25 часов | Провайдер забыл `reference` и заплатил второй раз | После 23 часов от запроса неизвестная провайдеру выплата не отправляется, а ждёт человека | `past 23 hours an unknown payout is held for a person, not sent again` |
| Исключение внутри `apply()` | Счёт мог остаться применённым наполовину, а движок продолжал отвечать | `apply()` отказывает в неизвестном типе до изменений; любое исключение останавливает движок, как упавший коммит | `an unknown event type is refused before anything changes`, `a throw inside apply stops the engine…` |
| Снапшот версии до выплат | Нет `payouts`, порога и id счёта: восстановление падало на первой выплате | `restore()` дополняет снапшот; id счёта передаётся явно, никогда не выдумывается — новый id при каждом рестарте дал бы выплате новый `reference` и вторую оплату | `a snapshot from before payouts restores with its account id given…` |

## Решения, принятые без ответа заказчика

- Время назад: `apply` никогда не откатывает торговый день. Отклонять или подтягивать запоздавшее `at` в движке — не решено.
- Повторный `cmdId`: сравниваются символ, сторона и количество (или позиция для закрытия); цена — нет, её ставит секвенсор.
- Цена закрытия ≤ 0 отклоняется так же, как при открытии.
- Колонка журнала остаётся `payload`. Если имя `event` нужно в базе — expand → migrate → contract за три деплоя.
- Упавший коммит останавливает движок навсегда; путь дальше — рестарт из снапшота и журнала. `drain()` после остановки отклоняется, а не делает вид, что всё записано.
- Дневной лимит остаётся по балансу, как в README.
- Закрытие проводит P&L и комиссию одной суммой с одним округлением (как было в коде). Если нужны две проводки — каждая округляется отдельно, и итог может отличаться на цент.

## Не проверено

- Записи, написанные версией без выплат, при восстановлении этой версией пересчитываются с новым округлением: сумма может отличаться на цент, а отказанное тогда открытие — пройти. Правильно — версия правил в каждой записи; пока восстанавливать журнал старой версии с её сделками этой версией нельзя.

- Postgres вживую: `PgJournal` проверен на заглушке, повторяющей поведение таблицы; базы в задании нет.
- Docker: тесты запускались через `npm ci --ignore-scripts && npm test` (вариант из задания), Docker на машине не запущен.
- Граница дня зависит от базы часовых поясов в Node; при смене правил перехода на летнее время разные версии Node могут разойтись.
